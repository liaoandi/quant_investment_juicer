# Weibo Crawl Handoff

## 当前目标

用户当前目标已经明确收敛为：

- 继续抓取微博账号「量化投资榨汁机」的最新内容
- 优先保证账号安全，不要触发反爬，不要因为高频接口访问导致封号
- 不再坚持走 `m.weibo.cn` API + cookie 重放路线
- 改为更保守的“已登录浏览器上下文里的低频页面抓取”

用户明确表达过两点：

- “不要让我被封号”
- `agent-browser` 路线先不折腾，最终接受继续走更稳的浏览器/Chrome 路线


## 已做过的尝试

### 1. `agent-browser` 方案

最初尝试把登录环节切到 `agent-browser`，采集继续留给 Python。

做过的事：

- 确认本机可运行 `npx agent-browser`
- 验证过 `agent-browser 0.23.3`
- 检查过以下 CLI 能力：
  - `agent-browser --help`
  - `agent-browser state --help`
  - `agent-browser auth --help`
  - `agent-browser cookies --json`
- 在微博场景里尝试过专用 session/profile：
  - `weibo_cookie_refresh`
  - `~/.weibo_agent_browser_profile`

遇到的问题：

- `agent-browser` 有全局 daemon
- 一旦 daemon 已经启动，后续再传 `--profile` / `--headed`，CLI 会提示 `ignored`
- session 和 profile 没有稳定强绑定
- 实测出现过：
  - `get url -> about:blank`
  - `cookies --json -> []`
- 因此这条路线不适合作为当前任务的主方案

结论：

- `agent-browser` 适合临时浏览器操作，不适合当前这个“稳定复用指定登录态做生产抓取”的场景
- 这条路线目前已放弃，不建议继续作为主线


### 2. Chrome cookie 重放路线

随后切到 Chrome cookie 方案。

做过的事：

- 发现本机 Chrome 存在 profile：
  - `Andi -> Profile 4`
- 用项目 `.venv` 成功安装并使用了：
  - `browser_cookie3`
- 用提权方式成功从 Chrome 读取微博 cookie
- 成功读取到 17 个微博 cookie，包括：
  - `SUB`
  - `SUBP`
  - `ALF`
  - `SCF`
  - `XSRF-TOKEN`
  - 其他微博相关键

实际结果：

- 默认 Chrome store 可解密后，接口校验返回 `login_required_api`
- 指定 `--chrome-profile Andi` 后，仍返回 `login_required_api`
- 当前环境变量里的 `WEIBO_COOKIE` 拿去实际探测时，还会命中 `432`

结论：

- 用户在真实 Chrome 页面里“能看微博”，不等于“把 cookie 拿出来重放给脚本就能打通 `m.weibo.cn` 接口”
- 现有这条 API 路线不稳定，继续硬刷有风险

## 当前最关键的结论

不是“脚本坏了”，而是“当前抓取器能拿到的登录态，不是完整可抓内容的登录态”。

用户明确表示：

- 他在自己的 Chrome 里肯定能正常看微博

但当前项目内可用的三种自动化入口都没能复用到那份完整状态：

- Chrome cookie 重放：失败
- Playwright 保存态：失败
- 页面级 Playwright 抓取：只能看到 `登录注册后查看更多微博`

## 当前最推荐的下一步

最值得继续尝试的是：

### 方案 A：直接复用真实 Chrome profile 做页面级抓取

这是我认为最稳、也最贴近用户真实登录环境的路线。

建议步骤：

1. 让用户先完全关闭日常 Chrome
2. 在新脚本里增加对 `launch_persistent_context(profile_dir=真实 Chrome Profile)` 的支持
3. 直接挂：
   - `/Users/antonio/Library/Application Support/Google/Chrome/Profile 4`
4. 只做低频页面抓取，不打 API
5. 先试：
   - `scrolls=1`
   - `max-posts=5`
6. 如果能看到微博列表，再逐步放大到非常保守的增量抓取

风险说明：

- 真实 Chrome profile 被 Chrome 占用时，Playwright 可能打不开或冲突
- 所以必须先让用户关闭 Chrome


### 方案 B：继续研究为什么 Playwright 登录态是“半登录”

这条也能做，但我认为优先级低于方案 A。

方向包括：

- 登录后是否实际落到了 `m.weibo.cn` 而不是其他微博域
- 是否需要在登录后手动访问一次：
  - `https://m.weibo.cn/u/6937480224`
- 是否需要额外等待站内跳转完成后再保存 storage state
- 是否需要在同一上下文中保持更多浏览器痕迹

但这条路线不如直接复用真实 Chrome profile 省力。


## 安全要求

用户对安全非常敏感，后续必须遵守：

- 不要高频请求
- 不要多线程并发
- 不要暴力翻页
- 不要高频重试
- 一旦出现 `432`、`login_required`、登录提示、验证码等风控信号，立刻停止
- 优先页面级顺序抓取，少量、慢速
